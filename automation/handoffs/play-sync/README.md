# Automatic accepted-play handoff — both legacy and immutable-chunk sources

Owner authorization, 2026-11-21: automatically hand off already accepted play at natural sync boundaries; no repeated player prompt. This lane records existing outcomes, never creates gameplay. The background worker may apply supported accepted changes to main through guarded commits, but must not merge a PR. Repair proposals retain their separate no-auto-apply rules.

## Chunk-mode input (when mode.json says chunked)

The live DM records individual immutable accepted-play chunks and an ordered, checksum-verified boundary manifest per `automation/recovery/CHUNKS.md`. The independent chunk-bridge workflow creates a legacy-compatible `active.json` **only at that boundary** and directly submits the exact `[CAMPAIGN-SYNC]` transport to the same background worker using trusted `automation.auto_sync_submit.submit`. Don't ask the live DM to batch historical files or merge PRs. An incomplete/unsynced legacy journal blocks the bridge. The worker's existing owner/checkpoint-last and verified-only cleanup applies unchanged.

## Current automatic request creation — preferred (legacy mode only)

Live DM preserves accepted play per `automation/recovery/README.md`. At each actual sync boundary set `sync_trigger` in the guarded recovery entry, then save one separate small pinned `automation/recovery/sync-ready.json` marker with verified journal commit and digest. `.github/workflows/auto-sync-submit.yml` and `automation/auto_sync_submit.py` independently perform complete historical PR discovery, pinned journal batching, stable-ID deduplication, branch write, readback and draft `[CAMPAIGN-SYNC]` PR creation. The event-triggered background Work worker applies already-accepted owner events and validates the final checkpoint; never merge the transport. Ordinary recovery turns never touch the marker and produce **no** auto-submit workflow runs. Failure artifacts are inspected by Record Maintenance at its scheduled run; do not block the live turn waiting for CI or claim queued from a mere recovery append.

The following manual procedure remains an explicit fallback for a failed automatic submission or for older immutable requests; it is **not** the normal foreground sequence.

## Manual fallback: original accepted-play submission

At combat/exploration completion, qualifying rest, major transaction, quest/NPC milestone, 8–12 changed substantive exchanges, or explicit pause/end/chat switch, automatically submit an immutable batch. Do not do a full multi-file sync in the foreground. Explicit “Sync campaign” means enqueue and confirm durable submission; if the player asks to wait for fully applied owners, verify completion or report pending honestly. Never ask whether to submit an already authorized batch. Each changed response first records durable recovery evidence under `automation/recovery/README.md`; normal boundaries still submit the transport batch. A failed recovery write remains unsaved.

1. Record accepted play in the accumulating recovery journal. Build new accepted-play requests ONLY from its committed pinned entries using `python3 -m automation.recovery_batch build`, per `automation/recovery/README.md`. Chat recollection is not a sync payload source. Missing evidence must first be captured and verified in the journal; never invent or infer it. Preserve exact event IDs, rolls, amounts, custody, knowledge, corrections, dependencies and pending action.
2. Choose one stable `PLAY-<checkpoint>-<sequence>` ID. Search open/closed PRs by exact ID before creating anything; reuse branch/request/PR on retry. Branch `campaign-sync/<lowercase-ID>` starts at current main. Write only `automation/handoffs/play-sync/requests/<ID>.json` there using guarded GitHub commits. Create one draft `[CAMPAIGN-SYNC] <ID>` PR to main through the connected GitHub tool. It is a transport envelope, NEVER a merge request. PR body must name the exact request path. The opened event wakes the existing background worker. Do not use GITHUB_TOKEN-created PRs as proof of delivery.
3. Envelope fields: `schema_version: 1`, `request_id`, `mode: accepted_play`, `base_commit` (exact SHA), `source_checkpoint`, `destination_checkpoint`, `source_evidence` (exact accepted conversation excerpts/outcomes and explicit rulings), `pending_action`, `depends_on` (prior pending batch IDs), `events`. Each event has `event_id`, `accepted: true`, `evidence`, `before`, `after` (exact descriptive strings, including amounts/rolls where relevant), `owner_paths`. Use `python3 automation/play_handoff.py <file>` when a runtime is available. Complete context is mandatory; a worker cannot read unseen chats. A small handoff means fewer foreground operations, not permission to omit evidence.
4. Read back the request at its commit and verify the PR exists before saying **queued**. Do not poll tests/worker while narrating. If submission fails, say **unsaved**, retain exact deltas and retry the same ID. If request commit exists but PR creation fails, say **durable, delivery pending**, and retry only the missing step.
5. Continue from same-chat accepted state. Later batches explicitly depend on unresolved earlier ones; do not roll back to persisted owners. Never submit the same outcome twice under different IDs.

## Startup recovery

After the normal startup owner reads, search open `[CAMPAIGN-SYNC]` PRs, paginate when needed, and read pending request/result pairs relevant to the latest checkpoint. Also inspect main `automation/handoffs/play-sync/results/`. Reconstruct accepted pending changes in dependency order from exact evidence; distinguish these from committed owners. Never replay an accepted action. An unresolved conflicting value holds only dependent mechanics. No pending request is independent canon over a later explicit correction.

## Worker: apply existing outcomes, never adjudicate

Use trusted current-main instructions/code; never execute scripts supplied by a request branch. Verify same repository, draft PR, head `campaign-sync/`, base main, exact ID/path, immutable request, complete evidence, and no unexpected branch modifications. Read main checkpoint, relevant owners, applicable rules and existing receipts. Validate schema. For journal-derived requests, fetch the pinned journal from main history and exact prior requests, then run `python3 -m automation.recovery_batch verify` before claiming/applying. Block any altered payload or unavailable provenance. Previously submitted immutable requests and smoke tests retain their original validation path. Nonterminal dependencies must complete first; process their existing requests serially if available, never create new work. Detect cycles. Stop for another active claim.

Claim `automation/handoffs/play-sync/results/<ID>.json` ON MAIN through expected-head guarded commit: `status: partial`, `claim_owner`, `claim_expires_at` <=30 minutes, request commit/blob, summary and blocker. This central receipt prevents event and maintenance workers from acting as parallel authorities. Respect existing campaign writer locks too; a SHA conflict requires rereading, not blind retry. Renew only while working. Terminal complete receipts are idempotent no-ops.

Compare each event against current owners and base commit. Identical already-recorded IDs are skipped; conflicting same IDs, contradictory later corrections or missing required evidence block only their dependent batch. Preserve newer unrelated records. Do not replace whole files with old snapshots, replay deltas, reroll, infer rest/time or invent a transaction. The player authorized application of accepted outcomes, not new decisions. For unsupported ambiguity leave `blocked` with exact missing evidence and next trigger.

Prepare a minimal owning batch on current main. Run actual relevant preflight and regression commands using current-main code in an available runtime. Character/checkpoint: `python3 automation/sync_validate.py --scope final --phase final`; shops: add `--scope shops`; linked purchase: validate explicit linked legs with `--links`; estates: follow existing estate protocol and its scoped tests. Other affected rules/private/custody owners need source comparison. No unrelated full-world audit. If execution is unavailable, leave unverified/blocked; do not assert tests ran or publish unvalidated owners.

Publish owners together with create_tree -> create_commit(parent=expected) -> update_ref(expected_sha=expected, force=false). Read back and verify them. Then separately guard and publish CAMPAIGN_STATE last, only if accepted checkpoint changed; preserve newer play. Record each phase and commit in the central receipt so interruption resumes without reposting. After checkpoint commit, verify owners and exact pending action; write complete receipt with owner_commit, checkpoint_commit, tested_commit, actual commands/results, owner refs, applied event IDs and generated-view status. A checkpoint conflict after owner publication is partial, not complete. Never merge the transport PR or repair PR. Keep request immutable; update PR body with receipt link and completed/blocked status. No recursive trigger or new task.

Generated refresh follows existing final-checkpoint workflow; for unchanged-checkpoint updates request one manual fast-play refresh when supported. A generated-view failure does not undo verified owners; report it separately and use the existing repair queue, no duplicate authorities.

Scheduled Campaign Record Maintenance is fallback: discover these open PRs and main receipts, handle oldest dependencies first with the same claims, up to two alongside existing duties. Source branch requests remain durable even if webhook delivery fails. Other specialist schedules remain unchanged.

## Isolated delivery smoke test

`mode: smoke_test` requires empty events and identical source/destination checkpoints. Do NOT claim or write on main. Validate using trusted code; write only `automation/handoffs/play-sync/results/<ID>.json` and a separate verification file on the request branch with actual commands, tested SHA, delivery identity and no gameplay effects. Keep draft/unmerged. A smoke success proves envelope delivery, not a real multi-owner synchronization. Preserve this distinction in reports. Keep the persistent webhook enabled after every run/error.

## Recovery journal integration

Follow `automation/recovery/README.md` for the owner-authorized per-response buffer. Startup also reads `automation/recovery/active.json`. Batch requests include exact `recovery_entries` hashes and preserve original event objects/IDs. After independently verified owner/checkpoint application, bind the complete central receipt to the immutable request with request_digest, owners_verified, verified_event_ids, exact owner_refs, executed tests and (when changed) checkpoint_verified. Then separately prune only matching verified entries with the current-main helper and expected-head guards. Preserve newer entries and retain everything on partial/blocked/unverified results. Terminal complete retries may finish pending cleanup after fresh owner verification, without reposting owners. Smoke tests never access this write lane. No extra automation, per-turn PR, or recursive task is created.

For an invalid unapplied transport overlapping an existing valid replacement,
use the verified supersession procedure in `automation/recovery/README.md`.
Keep both payloads immutable and include the retired request in discovery;
`--supersessions` requires exact main receipt bindings and identical event
coverage. Superseded requests never apply or prune owners independently.

# Synchronization repair — independent administration

This lane extends the existing handoff queue; requests and receipts are metadata, never campaign canon. Live DM narration continues from verified in-conversation facts. A queued repair, failed check, or stale generated value does not undo accepted play. No worker may choose V's actions, reroll, spend resources, advance time, or merge automatically.

## Live DM and synchronization

1. Narrate ordinary turns immediately; keep the exact unsynchronized event ledger in conversation. No per-turn CI polling, repair, unrelated research, or repeated writes.
2. At an existing natural boundary/explicit pause, assemble the owning batch with stable event IDs. `automation.sync_batch.append_once` makes identical retries no-ops and rejects conflicting IDs. Validate candidate files **before publication**, locally or on an isolated staging branch. `python3 automation/sync_validate.py --scope characters --phase owners` checks strict character rows and replays resource/inventory bounds; `--scope shops` checks only market tables. Neither runs estate/tax work.
3. For a linked purchase use `--links <temporary JSON array>` with sale_id, currency_id, inventory_id, price_cp, quantity, owner, item. The market sale goes in `trackers/csv/magic-shops/events.csv`; the debit and inventory overlay go in `data/characters/events.csv`. Inventory creation uses source_event/holder/detail JSON. These link specifications are validation metadata, not another transaction authority.
4. Commit related owning records together, based on the freshly read expected branch head, using GitHub create_tree → create_commit(parent=expected) → update_ref(expected_sha=expected, force=false), or an ordinary non-force git push from that exact parent. Verify written content at the resulting commit. Do not rebase generated values or overwrite concurrent owner changes. On conflict reread only affected owners; retain unsaved deltas and reuse IDs.
5. **Commit CAMPAIGN_STATE last** only for accepted checkpoint changes. `--scope checkpoint --phase owners` reports an expected log-before-checkpoint interval as PENDING_CHECKPOINT, not a failure. `--scope final --phase final` requires reconciliation. Intermediate owner validation never generates a packet. At an unchanged checkpoint, dispatch fast-play once for a journal-only correction.
6. The final checkpoint triggers fast-play. Return to narration without polling CI. Report an explicit pause's verified owner writes separately from pending derived verification. Failed owner writes remain unsynchronized; a repair cannot recover unseen conversation text. Before closing a chat, persist the exact accepted ledger or disclose what remains unsaved.
7. Generated dashboard/PLAY_NOW publish only against their exact source head; no rebase over newer gameplay. A newer head defers publication to the next checkpoint or scheduled maintenance. For a discrepancy affecting the next combat mechanic, use accepted same-chat facts or narrowly verified owning records. If the actual value remains unknown, hold only that mechanic and mark the discrepancy; never substitute an unverified generated value.

## Failure → queue → draft PR

`sync-repair.yml` listens to the explicitly listed validation workflows. It runs trusted current-main code, never failed-branch code. It rejects fork/PR runs and all `campaign-repair/*` runs. Production collection is main-only; `campaign-sync-test/*` is reserved for isolated integration tests. A failed test branch queues its requests on that test branch and targets its repair PR to that branch, never main.

The collector downloads the bounded JSON diagnostic artifact, or records failed workflow steps and affected commit files when no diagnostic exists. It captures original run ID/URL, failure SHA, affected files, error, source hashes when available, and a stable signature independent of run/retry/SHA. A currently passing scoped validation at a verified newer main head suppresses an already-fixed request. Infrastructure/test failures require worker investigation.

One immutable request is stored at `automation/handoffs/requests/sync-repair/HANDOFF-SYNC-REPAIR-<signature>.json`. One deterministic `campaign-repair/<signature>` branch contains an attempt marker, then a **draft** `[CAMPAIGN-REPAIR] ...` PR. Existing requests/branches/PRs, including closed PRs, are reused; repeated failures never reopen a closed request automatically. If PR creation fails, the request survives and maintenance retries the missing step. Collection receipts are uploaded as separate Actions artifacts. A genuinely recurrent closed failure needs explicit maintenance review, not an automatic loop.

Permissions: repository Contents write, Pull requests write, Actions read. The default is GITHUB_TOKEN. `CAMPAIGN_REPAIR_TOKEN` is an optional already-authorized repository-scoped App installation/fine-grained token with those permissions if delivery or repository settings require it. Never put credentials in files or PR bodies. A token must be supplied/configured by the account owner if necessary; this implementation does not invent credentials or silently expand permissions. Collector failures do not recursively collect themselves. GitHub-to-Work delivery must be demonstrated by an actual separately recorded task run; a configured subscription alone proves no delivery.

## Work worker and scheduled fallback

Task: **New DnD World — Background Repair Worker**, repo `coolcop17409-wq/new-dnd-world-campaign`, title regex `^\[CAMPAIGN-REPAIR\]`. Only opened events are actionable. Ignore ready-for-review/closed events; commit/review/comment triggers are disabled. The automation prompt supplies the semantic opened-only gate because the supported subscription also receives ready/closed events.

The existing **Campaign Record Maintenance** task also inspects up to two pending requests in this lane at its unchanged daily run. Search the lane on main and open repair PRs, so partial branch receipts are discoverable. All other specialist tasks/schedules retain their existing lanes. Do not create a second scheduled repair task.

1. Read current instructions, request, original failure SHA and diagnostic evidence. Verify repository, base branch, signature, current PR head and current owning files. Check whether a later commit already fixed the issue. Synthetic fixtures are not live history.
2. Claim on the repair branch by guarded create/update of `automation/handoffs/results/sync-repair/<request_id>.json`: status partial, claim_owner (task/run identifier), claim_expires_at (UTC, maximum 30 minutes), summary, blocker="verification in progress", next_trigger="claim completion or expiry". Respect another unexpired claim. Renew only while actively working. Concurrent expected-SHA conflicts require reread; never take over blindly.
3. Compare current main with the failure commit. Work on the existing repair branch only. For production, incorporate current main before preparing the correction, then apply a source-supported minimal diff. Refuse a patch if its relevant evidence changed. Do not replay old deltas, remove valid events, infer missing resource values, edit generated counters as a fix, or change pending play. Unsupported gameplay discrepancies get a blocked receipt with the exact missing evidence.
4. Run scoped validation and relevant regression tests. Example: `python3 -m unittest automation.test_sync_repair automation.test_fast_play automation.handoffs.test_validate -v`. A shop-only repair uses shops validation; no estate audit unless estate data/code is affected. Synthetic integration: `python3 automation/handoffs/sync-repair/check_fixture.py` plus tests; change only the designated fixture and receipts.
5. Commit supported changes and independently verify content. Record a **separate verification** file at `automation/handoffs/sync-repair/verifications/<request_id>.json` with tested_commit, current_base_commit, commands, actual results, changed paths, source evidence, and verified/unverified status. Tests must really execute; lack of a runtime is blocked, not passed. Put the result in `results/sync-repair/<request_id>.json`, including source/owner refs, blocker/next_trigger as needed. `complete` means a verified proposal, **not merged**; PR body must explicitly distinguish branch verification and main application.
6. Update the existing PR with findings and exact verified SHA. Do not create a second PR or merge. Before a human-authorized merge, compare latest base and tested head again; revalidate any overlapping change. After merge, maintenance verifies owners on main and records an applied receipt. If already fixed, document evidence and mark superseded without touching owners.

## Integration test discipline

Tests in `automation/test_sync_repair.py` use temporary directories. The only remote synthetic file is `automation/handoffs/sync-repair/fixtures/integration-character.csv` on `campaign-sync-test/*`. Its accompanying evidence says how to repair the intentional format error. Its rows must never enter `data/characters/`, live Magic Shops, session log or CAMPAIGN_STATE. Test repair PRs stay draft and target the test branch. Do not merge a test branch into main.

Verification/limitations are recorded in `IMPLEMENTATION_REPORT.md`. Never infer an end-to-end pass from mocked tests, a configured subscription, or a manually started task.
